# 杜甫全程玩家角色：步骤三至步骤十实施提示词

日期：2026-10-22  
用途：将本文各段提示词按顺序交给编码助手执行。每次只执行一个步骤，确认该步骤的代码、测试和交接说明完成后，再进入下一步。  
总方案：`docs/杜甫全程玩家角色-修改实施方案.md`

## 使用说明

1. 步骤三依赖总方案中的步骤一、步骤二已经完成：剧本生成链路已经统一，且已有稳定的玩家外观配置与角色档案纯逻辑。如果前置代码尚不存在，执行者应先核实并明确报告，不得自行发明另一套不兼容结构。
2. 每个步骤都要在当前脏工作区上增量修改。现有改动都属于用户，禁止重置、覆盖或顺手整理无关文件。
3. 所有正式剧本修改只能落在 `docs/杜甫行迹剧本-全22地点-含分镜.md`，运行时剧情文件由统一构建脚本生成，禁止直接长期维护生成文件。
4. 未经明确要求，不部署云函数、不上传云素材、不发布小程序、不清理真实用户数据。
5. 每个步骤结束时都要说明：改了什么、为什么、运行了哪些检查、检查结果、仍有哪些需要下一步处理的问题。
6. 如果实际代码与提示词中的文件名或结构已经变化，先寻找当前等价实现，再按同一产品行为修改；不得为了匹配提示词恢复旧代码。

## 步骤三提示词：完成旧数据迁移、云同步与清除语义

```text
请实施《docs/杜甫全程玩家角色-修改实施方案.md》的“步骤三：完成旧数据迁移、同步和清除”。这是编码任务，请直接修改代码并验证，不要只给建议。

【已确定的产品规则】
1. 本轮只为杜甫线创建全程玩家角色；李白、苏轼保持原状。
2. 玩家只选择三种外观之一并填写姓名。外观不绑定职业、能力、初始信任、剧情分支、奖励或难度。
3. 新角色资料按人物线保存，建议结构为：
   playerProfiles.dufu = {
     version: 1,
     avatarId: 'avatar01' | 'avatar02' | 'avatar03',
     displayName: string,
     confirmed: boolean,
     createdAt: number,
     updatedAt: number
   }
   如果步骤二已经确定了等价字段或 API，以步骤二现有实现为准，不要再造第二套结构。
4. 角色姓名与现有账号昵称 userNickname 完全分开。
5. 旧泰山身份只迁移外观：
   fellowScholar -> avatar01
   mountainGuide -> avatar02
   passingTraveler -> avatar03
6. 旧身份迁移生成的资料使用默认名“寻迹者”，并标记为待用户确认；已有合法且已确认的新资料永远优先。
7. 旧 trustEvents、tasks、见证物、地点进度、检查点、锚点和学习成果不得因迁移而删除。旧信任以后不再影响新角色剧情，但本步骤不粗暴清空旧兼容数据。

【开始前先做】
1. 阅读总方案、玩家外观配置、角色档案纯逻辑、progress/sync 及云端 merge 实现。
2. 查看 git status，明确相关文件已有的用户修改；只做本步骤需要的增量改动。
3. 找到当前进度 schema 版本、snapshot、mergeRemote、resetAll、云端 mergeSnapshot、clearState 和 deleteAccount 的真实入口。
4. 运行与存档同步相关的现有测试，记录哪些是原本就失败的，避免把旧失败误算成本轮回归。

【需要实现】
A. 本地存储
1. 在统一进度层增加 playerProfiles 的读取、创建/确认、编辑和删除能力。页面不得直接自行维护另一个 storage key。
2. 所有写入先通过步骤二的规范化与白名单校验；非法人物线、avatarId、姓名、时间字段不得进入正式档案。
3. 接入 progress.snapshot()、progress.resetAll()、导出 KEYS/API，以及必要的变更通知。
4. 将 schema 升级做成幂等迁移。每次重复运行结果一致，不能覆盖用户已经确认的新角色。

B. 旧泰山身份迁移
1. 从 locationProfiles.dufu.taishan.roleId 读取旧值，仅按上述映射预选外观。
2. 只有合法旧角色且不存在合法新角色时，创建 confirmed:false 的迁移草稿。
3. 非法旧角色或没有旧角色时不生成错误档案。
4. 迁移后保留旧 locationProfiles 原数据，以免破坏任务、见证物和老版本兼容。
5. 本地启动时迁移一次；云端旧快照稍后合并进本地后，还要再次幂等补全，避免只在 pull 之前迁移导致遗漏。

C. 本地与云端合并
1. playerProfiles 必须同时进入：客户端 snapshot、客户端 mergeRemote、服务端 mergeSnapshot、服务端空快照。
2. 缺少 playerProfiles 表示旧客户端未提供该字段，不得据此删除云端已有角色。
3. confirmed:true 优先于 confirmed:false。
4. 两份都是已确认资料时，以 updatedAt 更新的一整份为准，不能分别拼接姓名和外观。
5. updatedAt 相同时必须有稳定、与输入顺序无关的平局规则，保证 merge(A,B) 和 merge(B,A) 收敛到同一结果。createdAt 保留合法的最早值。
6. 本地和服务端使用同一规则，最好复用同一组纯函数或使用同一批契约测试验证。
7. 服务端保存后若现有协议允许，应返回合并后的权威快照或角色档案；客户端吸收该结果，避免本地显示刚编辑的值而云端保留另一份。
8. 对明显异常的未来时间戳采用项目一致的规范化策略，并在测试中固定当前时间或使用可注入时钟，避免不稳定测试。

D. 清除、重新开始和删除账号
1. resetAll 和云端 clearState 都要清除 playerProfiles；账号昵称保持原有独立语义。
2. 更新“清除进度”的相关说明文本，使用户知道杜甫角色资料也会被清除。
3. 检查 utils/sync.js 的在途 pull/push、generation、stop、waitForIdle。确保清除过程中旧请求不会在本机立即回填已清掉资料。
4. 若项目当前已经有服务端重置代次/墓碑机制，接入并测试；若没有，不要在本步骤悄悄引入未经设计的大规模协议。请明确报告“另一台离线设备的旧快照仍可能复活已清进度”这一边界，并把服务端重置代次作为独立后续项。不得声称普通空快照已经解决跨设备复活。
5. deleteAccount 维持永久删除现有整份用户档案的行为，并验证新增字段不会单独残留。

【测试要求】
至少覆盖以下行为，优先扩展真实的 tools/test-sync.js、test-location-progress.js、test-account-deletion.js 或新增聚焦的纯逻辑测试：
1. 三种旧 roleId 分别迁移为正确 avatarId。
2. 非法旧 roleId 不生成正式资料。
3. 迁移重复运行幂等。
4. 已确认新资料不被旧迁移草稿覆盖。
5. 云端旧快照在首次本地迁移之后才到达，仍能正确补全。
6. 缺 playerProfiles 的旧客户端快照不会删除新角色。
7. confirmed 资料优先、updatedAt 冲突选择、同时间戳稳定平局。
8. 客户端与服务端合并同一批输入时结果完全相同。
9. resetAll、clearState、deleteAccount 对新增字段的行为正确。
10. 现有地点进度、任务、锚点、见证物没有因迁移丢失。

【范围限制】
本步骤不做角色创建页面，不接聊天页，不改22地点剧本文案，不改AI提示词，不生成或上传图片，不部署云函数。

【完成后交付】
给出修改文件清单、数据结构和合并规则摘要、迁移示例、测试命令与结果，以及仍存在的跨设备清除边界。不得只说“已完成”。
```

## 步骤四提示词：接入角色创建入口与编辑页

```text
请实施《docs/杜甫全程玩家角色-修改实施方案.md》的“步骤四：接入创建入口和角色编辑”。直接完成代码、样式和必要验证。

【前置条件】
1. 步骤二已经提供三种外观的白名单配置与姓名规范化逻辑。
2. 步骤三已经提供按人物线保存的 playerProfiles、迁移、同步和清除 API。
3. 如果这些前置内容在当前代码中不存在或接口明显不同，先核实并报告具体缺口，不要在页面里临时写一套 wx.setStorageSync 旁路实现。

【已确定的体验】
1. 只对杜甫线启用角色创建；李白、苏轼入口完全保持现状。
2. 用户选择现有三张玩家立绘之一，只代表外观。
3. 用户填写角色姓名；默认名“寻迹者”，建议1至8个允许字符，最终规则以步骤二公共函数为准。
4. 首次选择杜甫：角色创建 -> 现有穿越转场 -> 杜甫行迹地图。
5. 已有 confirmed:true 的合法杜甫角色：直接走现有穿越转场，不重复弹出。
6. 迁移生成的 confirmed:false 草稿：预选旧外观和默认名，要求用户确认一次。
7. “我的”页提供“杜甫线 · 我的角色”卡片和编辑入口。编辑外观或姓名不清除进度。
8. 重温不提供临时换角色入口。

【创建页要求】
建议新增 pages/player/player.js、json、wxml、wxss，并在 app.json 注册。若当前项目已有更合适的通用页面，允许复用，但必须只有一个统一入口。

页面内容：
1. 标题“我的角色”或“选择形象，留下你的名字”。
2. 三张形象卡。去掉“书生、引路人、旅人”等职业、能力、信任描述；可暂用“形象一／二／三”，或使用仅描述外观的短文案。
3. 姓名输入框，显示剩余长度或明确上限；输入值在保存前调用公共规范化函数。
4. 简短世界观说明：你会穿行于杜甫人生的重要时刻，岁月改变他的模样，而你保持初见时的样子；重逢时他记得已经共同经历的事。
5. 明确提示“形象不会影响剧情和学习内容”。
6. 确认按钮只有在外观和姓名合法时可用；连点只提交一次。
7. 异步图片晚到时不能把已经切换的选中状态改回旧形象；图片失败显示不裂图的占位。
8. 键盘弹出、小屏和微信胶囊安全区下，姓名输入与确认按钮仍可操作。

【入口路由】
1. 修改诗人选择页：点击杜甫时先读角色档案。未确认则进入创建页；已确认则沿用现有 transition 流程。
2. 创建页确认后继续进入原来的 transition?lineId=dufu，再由转场进入地图。取消/返回不保存半份正式角色。
3. 地图继续、地点卡、当前旅程、重温、聊天页直接URL都要经过同一角色守卫。不要只保护诗人选择入口。
4. 先执行地点是否存在和是否解锁的校验，再处理角色缺失，防止用户通过角色页绕过锁定地点。
5. 角色创建页只接受白名单化的返回意图，如 target=transition 或 target=chat、lineId=dufu、合法locationId、合法mode。禁止接收并跳转任意页面路径。
6. 用户从直接地点入口被送去创建角色，确认后回到原 locationId 和 mode；continue 保留原检查点，replay 仍从头回放。
7. 多入口同时触发或快速连点不能堆叠两个创建页、两次转场或两次 navigateTo。
8. 云同步尚未完成时，已有合法本地角色可继续。只有纯云恢复场景需要等待首次拉取作出结论，设置合理的无阻塞降级，避免先让用户重建、随后云端资料覆盖。

【编辑模式】
1. “我的”页角色卡展示当前形象和角色姓名，明确它不是账号昵称。
2. 点击编辑进入同一页面的 edit 模式，预填当前资料。
3. 保存时更新整份已确认档案和 updatedAt；取消不写入。
4. 保存后返回并刷新角色卡。地图和聊天页在 onShow 或下一个稳定节点刷新角色资料。
5. 编辑角色不能改写已保存的地点选择、通关状态、锚点、诗笺和检查点。

【样式与素材】
1. 可复用旧泰山角色浮层的宣纸、墨线、朱印视觉，但创建逻辑必须从 chat 页移出。
2. 复用现有三张 PNG 的云路径；不生成新素材、不上传云资源。
3. 旧职业文案不能继续显示在任何新创建或编辑界面。

【测试与验证】
至少验证：
1. 新用户选择杜甫只创建一次；三种外观均可保存。
2. 空姓名、纯空白、合法边界长度、超长、换行和无效字符处理一致。
3. 迁移草稿正确预填并转为 confirmed:true。
4. 取消、返回、快速双击不会写半份资料或重复跳转。
5. 从故事页、地图续玩、地点卡、直接聊天链接、重温进入时都能正确守卫和返回。
6. 锁定地点不能借创建页进入。
7. 编辑后刷新，账号昵称和剧情进度不变。
8. 选择李白、苏轼不出现杜甫角色页。
9. 图片失败和离线时页面仍可用。

如果项目的页面逻辑不便进行完整自动化测试，至少为角色守卫、返回意图解析和提交幂等写纯函数测试，并列出微信开发者工具人工检查项。

【范围限制】
本步骤不批量改剧本，不实现AI共同记忆，不改配音内容，不部署、不上传。聊天页只做防绕过角色创建所需的最小守卫，完整角色呈现留给步骤五。

【完成后交付】
说明实际交互路径、创建与编辑入口、路由白名单、修改文件、测试结果和需要在微信开发者工具验证的界面点。
```

## 步骤五提示词：让同一角色贯穿杜甫聊天流程并移除旧职业／信任玩法

```text
请实施《docs/杜甫全程玩家角色-修改实施方案.md》的“步骤五：把角色应用到整个杜甫聊天流程”。直接修改代码并完成回归验证。

【目标行为】
1. 杜甫22个地点都读取同一份 playerProfiles.dufu。
2. 玩家说话时显示自定义姓名和所选形象；外观与姓名在全线保持一致。
3. 三张外观不影响剧情节点、选项、题目、知识锚点、奖励或AI亲疏。
4. 泰山不再弹“这一程，你是谁”，不再存在职业身份、初始信任、信任称号或信任解锁。
5. 李白、苏轼保持现有行为，不显示杜甫角色资料。

【开始前】
1. 阅读 chat.js、chat.wxml、chat.wxss、story-variants.js、dufu-taishan-roles.js、progress 中角色及地点任务 API。
2. 搜索 currentRole、roleId、playerRoleType、playerAddress、localTrustScore、localTrustLabel、roleOverlayVisible、playerRoleId、relationshipStage、trustVariants、type:'trust' 等全部引用，建立删除/保留清单。
3. 检查当前杜甫22地点运行时数据是否真的包含 tasks、trust effects 或 role variants。以当前源稿和生成数据为准，不能按过期测试假设功能存在。

【需要修改】
A. 角色恢复和页面状态
1. 杜甫任意地点加载成功后、进入起始节点或检查点前，从全线角色档案恢复 displayName、avatarId 和图片。
2. 角色缺失或非法时调用步骤四的统一角色守卫，不在 chat 页重新维护一套泰山选择浮层。
3. 将 currentRole、playerRoleType 等容易误解为职业的状态改为 profile/avatar 语义；如果为兼容暂时保留字段，应保证其值不再作为剧情条件。
4. 异步解析玩家图片时加入请求/角色版本校验，防止旧图片响应覆盖编辑后的新形象。
5. 页面卸载、切线和重新进入时清理玩家状态，避免从杜甫切到李白或苏轼后残留姓名与立绘。

B. 对话和选择呈现
1. 固定 speaker:'player' 的 talk 节点使用 displayName 和玩家立绘。
2. 普通 choice 通过 playerChoiceNode 转成玩家发言时，也使用同一资料。
3. 检查动作型选择：如“（沉默）”“（望着山下）”不能被当成角色口述。为解析器增加清晰的数据语义，如 actionOnly 或显式 spokenText；不要用脆弱的括号文本猜测作为长期规则。
4. NPC说话时按当前布局显示；玩家立绘是否作为倾听者出现，遵从现有画面空间和设计，不要求所有旁白一直显示玩家。
5. AI自由对话消息区的用户侧可显示角色姓名/头像，但不把它误作NPC对白或TTS节点。

C. 顶部信息与旧UI退场
1. 将顶部身份条改成简洁的“同行者 · {displayName}”或等价角色信息。
2. 移除职业类型和信任称号。不要显示关系阶段、好感数值或等级。
3. 泰山专属角色浮层及对应事件处理器从WXML、JS、WXSS中删除或彻底停用；确认无不可达死代码和无效绑定。
4. 清理“以此身份进入／重温”“初见／逐渐信任／袒露心事”等已废弃文案。

D. 旧职业和信任逻辑退场
1. 正式游玩不再调用 chooseLocationRole，也不再根据旧roleId发初始信任。
2. 杜甫新流程不再把 roleId/trustScore 传入剧情节点解析条件。
3. 不执行 effect type:'trust'；任务奖励中的 trustPoints/trustEventId 不再改变UI或解锁内容。
4. 地点任务若当前剧本确实存在，应保留任务步骤、完成状态和见证物功能，但必须和信任解耦。当前源稿没有任务时，不为复活过期样板而新增任务。
5. 旧 locationProfiles 数据继续可被迁移和旧版本读取；本步骤不批量删除用户本地数据。
6. story-variants.js 如果仍为其他功能服务，保留安全兼容；当前杜甫新线路不再使用职业/信任条件。若确认全项目无消费者，再连同失效测试有依据地清理。
```
