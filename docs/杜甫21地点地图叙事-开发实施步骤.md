# 杜甫 21 地点地图叙事：开发实施步骤

> 方案基线：`docs/杜甫行迹剧本-全21地点.md`  
> 上层方案：`docs/地图叙事与地点级剧本改造计划.md`  
> 编制日期：2026-10-17  
> 目标：先用杜甫线做出可完整体验的地点级样板，验证交互与叙事方式，再将同一架构推广到李白、苏轼。

## 一、本次样板做到什么程度

杜甫样板完成后，用户应当能够完成以下闭环：

1. 启动小程序并完成合规确认；
2. 在首页选择杜甫；
3. 进入杜甫 21 地点地图；
4. 首次仅地点 1 可进入，其余地点灰色锁定；
5. 当前地点旁显示一枚闪烁的“行”印章；
6. 点击地点或印章，打开地点卡并进入对应地点剧本；
7. 中途退出后，再次进入可从最近稳定剧情节点继续；
8. 完成地点后，在剧情页内展示地点诗笺；
9. 点击“收下诗笺，前往下一站”返回地图；
10. 已完成地点常亮，下一地点解锁并出现闪烁印章；
11. 普通地点解锁后呈棕黄色，关键地点解锁后呈红色；
12. 已完成地点可以从头重温，也可以查看“一诗一识”和完整诗笺；
13. 完成第 21 地点后显示杜甫全线完成状态。

本轮重点是验证产品体验，不要求一次补齐全部新场景图和 TTS。没有专属素材的地点先复用相近素材，但必须在数据中明确标记素材缺口，便于后续替换。

### 2.2 接入前必须处理的问题

| 问题 | 当前表现 | 处理方式 |
|---|---|---|
| 地点数变化 | 旧地图 19 处，新剧本 21 处 | 杜甫地图完全以新清单重建 |
| 新节点类型 | 剧本含 `anchorCard`，现有引擎不识别 | 先扩展引擎，再导入剧本 |
| 考据语义不匹配 | 多个 `trap.text` 是提问，现有 UI 却让玩家判断“这里不对” | 接入时把种子台词改成明确的错误陈述，或新增知识问答类型；样板优先改写种子台词 |
| AI 知识库仍按时期索引 | 云函数只认识 `p1...p4` | 建立地点到时期的知识库映射，后续再细分地点史料卡 |
| 场景素材不足 | 新增地点没有专属场景图 | 用场景别名复用现有图片，并输出素材缺口表 |
| 年龄立绘不足 | 七岁杜甫没有专属儿童立绘 | 技术样板先复用 p1 立绘；正式版补儿童杜甫 |
| 普通地点无 `anchorCard` | 剧本文档说明与代码不完全一致 | 所有地点通关都生成轻量诗笺；仅关键地点显示完整知识卡 |
| 终点复用 `a1` | 湘江 `anchorCard` 再次使用 a1，可能被去重逻辑吞掉 | 终章卡使用独立展示 ID，或加 `repeatable` 展示但不重复计数 |
| 同城多次到访 | 洛阳、长安有多个时间节点，地图坐标容易重叠 | 使用独立地点 ID，并对同城节点做小幅坐标偏移 |

## 三、技术策略：先做双轨兼容，不一次推倒全部主线

杜甫改成地点模式时，李白和苏轼仍保留时期模式。注册表为每条人物线增加叙事模式：

```js
{
  id: 'dufu',
  narrativeMode: 'location',
  locations: [],
  locationQuests: {}
}
```

```js
{
  id: 'libai',
  narrativeMode: 'period',
  periods: [],
  quests: {}
}
```

这样可以做到：

- 杜甫先展示 21 地点新体验；
- 李白、苏轼现有功能不被杜甫改造阻断；
- 地图和对话页通过统一适配层判断使用 `locationId` 还是旧 `questId`；
- 杜甫样板确认后，再把李白、苏轼迁到地点模式；
- 全部迁移完成后才删除时期模式兼容代码。

## 步骤 1：把 Markdown 剧本转换为稳定的运行时数据

### 工作内容

1. 新建 `tools/build-dufu-locations.js`；
2. 读取 `docs/杜甫行迹剧本-全21地点.md` 中的 21 个 JavaScript 代码块；
3. 提取每个 `QUEST_*` 对象；
4. 按附录顺序输出到 `line-dufu-locations.generated.js`；
5. 在生成文件头写明来源文件和生成时间，不允许手工编辑；
6. 生成器增加 `--check` 模式，CI/自测时只验证生成结果是否过期，不重写文件。

### 生成时校验

- 必须恰好 21 个 quest；
- ID 必须与附录一致且不能重复；
- 每个 quest 必须有 `id/title/range/start/nodes`；
- 从 `start` 出发必须可达 `__end__`；
- `choice.options` 的 `next/result` 必须存在；
- 节点类型只能是 `narrate/talk/choice/aiFree/reflect/anchorCard`；
- 所有 `scene`、`anchor` 和 `trap.anchor` 必须可解析；
- 输出总节点数必须为 262。

### 为什么不在小程序运行时读取 Markdown

Markdown 只是编剧工作稿，不适合进入小程序包后动态解析。构建时生成 JavaScript，可以保持编剧稿易读，同时让运行时数据稳定、可校验、无额外解析成本。

### 通过标准

执行以下命令能够输出 `21 locations / 262 nodes / ALL_OK`：

```powershell
node tools/build-dufu-locations.js --check
```

## 步骤 4：实现地点级进度与旧进度迁移

### 新存储字段

在保留旧字段的同时新增：

```js
locationStates
locationCheckpoints
locationRecords
selectedLineId
progressSchemaVersion
```

结构示例：

```js
locationStates: {
  dufu: {
    luoyang: 'completed',
    luoyang_shi: 'active',
    taishan: 'locked'
  }
}
```

### 解锁规则

1. 新用户仅 `luoyang` 为 `active`；
2. 完成当前地点，将其设为 `completed`；
3. 下一地点设为 `active`；
4. 其余地点为 `locked`；
5. 重温已完成地点不改变主线活动地点；
6. 完成 `xiangjiang` 后整条杜甫线完成。

### 旧时期进度迁移表

| 旧时期 | 对应新地点 |
|---|---|
| p1 | 1–6 |
| p2 | 7–9 |
| p3 | 10–13 |
| p4 | 14–21 |

迁移规则：

- 旧时期 `completed`：对应地点全部迁为完成；
- 旧时期 `active`：该时期第一个地点设为活动，其余锁定；
- 后续时期保持锁定；
- 旧锚点和诗笺记录不删除；
- 旧时期记录保留为只读历史，不伪造地点选择；
- 迁移写版本号且保证重复执行结果相同。

### 检查点规则

在以下时机保存：

- 成功进入一个新节点；
- 玩家作出选择；
- 考据挑战结算；
- AI 回复完成；
- `anchorCard` 收下；
- 页面进入后台或卸载。

恢复策略：

- 旁白/对话中途退出：从该节点全文开头恢复；
- 选择节点：重新显示选择，但已经落账的选择不得重复追加；
- AI 自由对话：恢复到该 AI 环节，不恢复用户与 AI 的正文；
- 反思节点：从反思开头恢复；
- 重温模式：使用独立临时状态，不覆盖正式检查点。

### 云同步

- `locationStates` 仍按 `locked < active < completed` 取较优状态；
- `locationCheckpoints` 按 `updatedAt` 取较新；
- `locationRecords` 按 `completedAt` 取较新，并保留最早 `earnedAt`；
- 本地和云端使用完全一致的合并断言。

### 通过标准

- 新用户只能进入地点 1；
- 旧 p1 已通关用户升级后地点 1–6 都完成；
- 重温地点 2 不会把当前地点从 8 改回 3；
- 多设备合并不会让已完成地点倒退。

## 步骤 5：扩展对话引擎支持地点剧本

### 路由参数

新增地点模式入口：

```text
/pages/chat/chat?lineId=dufu&locationId=luoyang&mode=continue
```

旧入口继续兼容：

```text
/pages/chat/chat?storyId=libai&questId=p1
```

### 初始化流程

1. 读取 `lineId/locationId/mode`；
2. 查找地点和地点剧本；
3. 校验地点是否允许进入，防止拼 URL 越级；
4. 解析地点场景与对应年龄立绘；
5. `continue` 读取检查点，`replay` 从 `start` 开始；
6. 统计本地点锚点和考据数量；
7. 开始节点流。

### 新增 `anchorCard` 节点

当前引擎遇到未知类型会直接通关，因此必须显式增加：

```js
case 'anchorCard':
  // 展示指定知识卡
  // 用户点击“收下”后再进入 node.next
  break;
```

要求：

- 不在卡片刚出现时立即进入 `__end__`；
- 用户可主动查看完整史料；
- 用户收下或完成自动收起后才推进；
- 已拥有锚点仍允许在终章作为总结卡展示，但不重复计数；
- 湘江终章的 a1 采用 `repeatable` 展示或独立总结卡 ID。

### 常见误解纠正（已替代旧版考据选择）

地点剧情不再使用 `trap.wrong/right/catchText` 或“这里不对”按钮。常见误解写入云函数知识卡的 `misconceptions` 规则：玩家没有提及则正常聊天；玩家把杜审言说成“初唐四杰”或提出相关疑问时，由本地规则稳定澄清为“文章四友”；玩家已经正确说出“不是初唐四杰”时不得误触发。

验证要求：错误陈述优先进入 `misconception` 阶段，不得因命中“杜审言”等关键词而被判成“答对了”，也不把纠错轮次计为已经掌握知识。

### AI 知识库兼容

建立地点到旧时期的映射：

```js
luoyang -> p1
luoyang_shi -> p1
...
yexian -> p2
...
xiangjiang -> p4
```

云函数查卡顺序：

1. 优先读取地点专属卡 `knowledge.dufu[locationId]`；
2. 没有时读取该地点的 `periodId` 卡组；
3. 兜底回复也按 `periodId` 选择，不因新 ID 返回空洞通用回复。

### 通过标准

- 21 个地点都能从 `start` 走到 `__end__`；
- `anchorCard` 不会导致提前通关；
- 7 个 AI 地点能正常问答、考据和继续剧情；
- 普通地点不依赖 AI，也能完整通关。

## 步骤 6：把地图改成杜甫 21 地点状态机

### 数据改造

杜甫地图不再读取时期状态，而是读取 `locationStates.dufu`。每个渲染对象至少包含：

```js
{
  locationId,
  seq,
  name,
  subtitle,
  x,
  y,
  state,
  importance,
  isImportant,
  isCurrent,
  showEntrySeal,
  scene,
  poemTitle,
  poemLine,
  knowledge
}
```

### 颜色优先级

```text
locked                         灰色
active + normal                棕黄色 + 呼吸
completed + normal             棕黄色常亮
active + key                   红色 + 呼吸
completed + key                红色常亮
```

关键地点在锁定时不得提前显示红色。

### 闪烁印章

在当前地点标记内部增加：

```xml
<view wx:if="{{item.showEntrySeal}}" class="entry-seal">行</view>
```

动效分两段：

1. 新解锁时执行一次“朱印落下”；
2. 落下后低频呼吸闪烁，直到地点完成。

交互规则：

- 地图上同时只能有一个闪烁印章；
- 点击印章与点击地点效果相同；
- 印章不能挡住序号和地名；
- 首次进入地点后可降低闪烁频率，但地点未完成前保持弱提示；
- 开启系统“减少动态效果”或低性能降级时，改为静态发光。

### 路线状态

- 两端均完成：实线常亮；
- 上一地点完成、下一地点活动：晕开或虚线流动；
- 后续锁定：灰色虚线；
- 通往关键地点的当前路线可以使用红棕色，但不能让未解锁地点提前显红。

### 地点卡

当前地点：

- 显示地点、年代、简介、代表诗句；
- 主按钮“继续此地故事”；
- 有检查点时显示“上次行至……”的轻提示。

已完成地点：

- 显示“一诗一识”；
- 按钮“展开诗笺”和“重温此地”。

锁定地点：

- 只显示地点名和“完成上一地点后解锁”；
- 不显示关键地点身份、剧情摘要和完整诗句。

### 通过标准

- 地图显示 21 个连续序号；
- 同城地点不完全重叠；
- 地点完成后只解锁下一处；
- 任一时刻只有一个“行”印章闪烁；
- 第 21 地点完成后没有活动印章。

## 步骤 7：在剧情结算中展示地点诗笺

### 组件化

从现有诗笺页抽取可复用的视觉部分，建立 `location-poem-card` 组件。组件接收：

```js
{
  lineName,
  locationName,
  range,
  poemTitle,
  poemLine,
  knowledge,
  choices,
  anchors,
  importance,
  completedAt
}
```

### 两种诗笺层级

普通地点轻量诗笺：

- 地点名与序号；
- 一句代表诗；
- 一个知识点；
- 本次完成印章。

关键地点完整诗笺：

- 普通地点全部内容；
- 关键选择；
- 知识锚点；
- 考据结果；
- 完整情感总结；
- 保存相册或分享能力。

### 通关顺序

1. `__end__` 写地点完成记录；
2. 解锁下一地点；
3. 当前页面展示地点诗笺；
4. 用户点击“收下诗笺，前往下一站”；
5. 设置 `app.globalData.mapFocus={lineId, locationId}`；
6. 返回地图并聚焦新地点；
7. 新地点播放落章与闪烁提示。

### 地图回顾

- 已完成地点点击后先展示“一诗一识”；
- 用户主动点击“展开诗笺”后打开完整卡；
- 不把完整诗笺永久铺在地图画布上；
- 原 `pages/poem` 保留为非 Tab 历史兼容页，暂不删除导出能力。

### 通过标准

- 通关后不再跳到独立诗笺 Tab；
- 地图可再次打开已完成地点诗笺；
- 重温产生的新锚点可补充，但不覆盖首次获得时间。

## 步骤 11：分段真机验收

不建议一次跑完 21 个地点才验收。按以下批次检查：

## 步骤 12：样板评审与是否推广

杜甫线完成后，不立即复制到另外两条线。先用以下问题判断方案是否成立：

1. 用户是否一眼知道下一地点在哪里？
2. 21 个地点是否太密或太长？
3. 普通地点 2–4 分钟是否合适？
4. 关键地点红色是否确实有“人生转折”的感觉？
5. 地点剧情结束后的诗笺是否自然，而不是重复打断？
6. 用户是否会主动点已完成地点回看“一诗一识”？
7. 首页选择人物、地图推进、剧情和成果之间是否形成清楚闭环？
8. 身份玩法未来加入时，地点开场是否留有足够接口？

只有杜甫样板得到肯定后，才按同一数据结构迁移李白和苏轼；若用户觉得 21 地点过密，应优先调整地图聚合与地点篇幅，而不是立刻继续批量写代码。
