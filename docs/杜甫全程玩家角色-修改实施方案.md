# 杜甫全程玩家角色修改实施方案

日期：2026-10-21（2026-10-22 复核更新）  
状态：步骤一至步骤六已完成；步骤六已完成 22 地点连续性审稿、自由对话上下文修订、重新生成与自动校验。  
适用项目：寻迹诗旅微信小程序。

2026-10-22 复核结果：两个杜甫构建入口已收敛到同一核心，22 地点、854 节点与磁盘派生产物一致；分镜映射为 84 镜有图、71 镜回退默认图，另有 2 张现存图未被当前镜头标记引用，构建时会明确警告。三个外观配置及玩家档案纯逻辑已补齐外观白名单、姓名控制字符、精确字段和时间戳校验，本地与云端合并规则一致。

## 1. 已确认的需求

| 项目 | 本轮确定的行为 |
| --- | --- |
| 范围 | 先完成杜甫整条人物线；李白、苏轼以后扩展 |
| 玩家形象 | 沿用现有三张玩家立绘，仅作为外观，不绑定职业和能力 |
| 玩家姓名 | 可以自定义，显示在玩家对白姓名栏和角色档案中 |
| 杜甫称呼 | 主要使用预先编写的固定称呼，不把自定义姓名拼入杜甫配音 |
| 时间设定 | 玩家穿越到关键人生节点，与杜甫重逢；玩家外貌不随年代改变 |
| 共同经历 | 杜甫记得已经发生的共同经历，未发生的事情不能提前知道 |
| 关系发展 | 通过对白、重逢和回忆体现，不设置好感分、关系等级或亲密度解锁 |
| 历史主线 | 外观和姓名不改变历史事件、学习内容、题目难度、奖励和剧情结局 |

本方案替代此前讨论中的“书生／引路人／旅人三职业分支”“每条线累计信任分”“重温换身份体验专属剧情”等建议。这些已不符合本次确认的需求。

### 建议采用的实施默认值

以下是便于直接实施的建议，不属于用户已逐项确认的额外需求；若后续调整，只影响对应局部：

- 功能名称采用“我的角色”，创建页使用“选择形象，留下你的名字”。
- 默认角色名为“寻迹者”；支持 1–8 个汉字、英文字母或数字，按 Unicode 字符计数；去掉首尾空白，不接受换行和控制字符。默认值直接填入输入框，清空后提示填写。
- 形象卡先采用“形象一／形象二／形象三”，不沿用书生、向导等职业标签。经实际预览后可以换成准确的服饰描述。
- 首次选杜甫时创建角色；已有角色直接沿用；直接进入地点时提供同一创建流程的兜底。
- 在“我的”页提供杜甫角色档案及“编辑形象与姓名”。这只是展示资料修改，不重置旅程；编辑中取消不写入。
- 重温沿用已保存角色，不再每次弹出选择，也不提供独立的临时角色存档。
- 穿越规则只在创建角色时简短说明；各地点继续用时间、地点和重逢自然衔接，避免每站重复播放穿越动画或叙述“睁开眼”。
- 玩家形象在自己说话和行动时出现；不要求人物立绘覆盖所有旁白、诗歌与结尾画面。

## 3. 最终体验

### 首次开始

1. 用户在现有诗人选择页选择杜甫。
2. 打开“我的角色”创建页：三张形象卡、姓名输入、简短设定说明。
3. 确认“以此形象出发”，保存杜甫角色档案。
4. 进入现有穿越转场，然后进入杜甫行迹地图。
5. 从已允许进入的地点开始；角色会自动带入全部 22 个地点。

建议说明文案：

> 你将穿行于杜甫人生中的重要时刻。岁月会改变他的模样，而你仍是初见时的样子；每次重逢，他都记得你们曾走过的路。

创建页可以补一句“形象不影响剧情和学习内容”，帮助用户安心选择。

### 再次进入及中途退出

- 再次选杜甫或从地图继续：读取同一角色，不重复创建。
- 进入泰山：直接使用全程角色，不再出现“这一程，你是谁”。
- 从任意已解锁地点直接进入而没有角色：创建后返回原目的地及原模式，保留检查点。
- 创建页返回或取消：不写半份角色，不写新检查点、不解锁下一站。
- 切换李白或苏轼：维持现有行为，不携带杜甫角色、姓名或记忆。
- 重温：使用当前角色的外观与姓名，但剧情记忆回到该地点当时。

## 5. 步骤二：定义外观配置及杜甫角色档案（已完成）

建议新增：

- `miniprogram/utils/player-avatars.js`：外观白名单、文案、素材键和旧角色映射。
- `miniprogram/utils/player-profile.js`：姓名规范化、档案校验和合并等纯逻辑。

角色档案通过 `progress.js` 的统一存储、变更通知及快照管理，不在页面里另写一套存储。

建议数据形态：

```js
playerProfiles: {
  dufu: {
    version: 1,
    avatarId: 'avatar01',
    displayName: '寻迹者',
    confirmed: true,
    createdAt: 0,
    updatedAt: 0
  }
}
```

设计约束：

- 人物线 ID 在外层，第一版只允许 `dufu` 创建和应用；保留后续扩展空间。
- `avatar01`、`avatar02`、`avatar03` 只是稳定外观 ID，不再让职业名成为逻辑条件。
- 素材映射继续使用现有云路径，不因更名重新上传一套相同图片。
- 不保存初始信任、关系分、职业、专属能力或角色解锁状态。
- `displayName` 是杜甫线角色名，与现有 `userNickname` 账号昵称分开；修改任一项不覆盖另一项。
- 姓名只按纯文本显示，前后端使用相同长度和字符规则；第一版无须传给 AI。
- `confirmed: false` 仅用于迁移生成的待确认档案，不让未确认资料覆盖用户明确设置的资料。
- 页面用统一读取方法恢复角色，不读取旧 `locationProfiles.dufu.taishan.roleId` 作为第二份有效角色。

完成标准：任意合法形象＋合法姓名均可稳定保存恢复；三张外观得到完全相同的剧情、学习条件和奖励。

## 6. 步骤三：完成旧数据迁移、同步和清除

主要文件：`utils/progress.js`、`utils/sync.js`、`cloudfunctions/story/merge.js`、`cloudfunctions/story/index.js`；核对登录返回的 `progress` 能保留新增字段。

| 旧泰山角色 ID | 新外观 ID | 保留的素材 |
| --- | --- | --- |
| `fellowScholar` | `avatar01` | `tang-young-scholar.png` |
| `mountainGuide` | `avatar02` | `tang-mountain-guide.png` |
| `passingTraveler` | `avatar03` | `tang-passing-traveler.png` |

- 已有合法新角色：直接沿用，不被旧角色覆盖。
- 只有合法旧角色：预选对应外观、默认名“寻迹者”，在下一次进入杜甫时确认一次；不要求从头玩。
- 旧角色非法或没有选择过：显示普通创建流程；地点、锚点、检查点继续保留。
- 旧 `trustEvents` 留在兼容存档中，但不再影响新剧情、称呼或奖励。

- 在本地启动以及每次云端合并后做幂等补全。仅做一次启动迁移会漏掉稍后才拉取的旧云数据。

### 6.2 新档案合并规则

新增字段必须同时进入本地 `snapshot()`、本地 `mergeRemote()`、服务端 `mergeSnapshot()` 和空档案清单。

- 输入先校验：合法人物线、外观 ID、姓名、版本和时间字段。
- 字段缺失代表该客户端未提供角色，不代表删除。
- 已确认档案优先于迁移待确认档案。
- 同为已确认档案时，按 `updatedAt` 取较新的一整份，避免把姓名和外观拼成用户未选过的组合。
- 同一更新时间出现冲突时，按固定的规范化字段排序打破平局，确保交换合并顺序也能收敛；`createdAt` 保留有效最早值。
- 保存时使用递增的本地更新时间；跨设备时钟偏差是时间戳合并的已知限制，遇到较远未来时间需规范化处理，并测试一致性。
- 服务端保存合并后的资料应返回权威角色结果，客户端接收更新，避免本地显示自己刚选的角色而服务端保留另一份。
- 旧客户端上传不带 `playerProfiles` 的快照时，服务端仍保留已存的新角色。
- 冷启动同步期间不要把“尚未收到云档案”当成“确实没有角色”；已有本地角色可先恢复，纯云恢复在首次拉取结束后决定是否创建。网络失败允许本地创建，后续按同一规则合并。

### 6.3 清除与重新开始

- 现有“清除进度”同时清除杜甫角色，并在文案中说明；账号昵称保持现有独立行为。
- 服务端 `clearState` 清空新角色字段；账号删除流程覆盖新增字段。
- 清除前暂停同步、等待在途保存结束、使旧拉取回调失效；成功后恢复同步，避免同设备旧请求把角色写回来。
- 多设备离线后的旧快照也可能把已清空内容合并回来。如验收要求“另一设备重新联网也不能复活进度”，需给学习档案增加服务端重置代次，旧代次快照被拒绝并要求重新拉取；不能声称仅清空字段就解决了跨设备复活。
- 重置代次只控制档案生命周期，不改变李白／苏轼业务玩法；升级时服务端兼容首次旧快照，重置后阻止过期快照恢复。

完成标准：退出重进、换设备、旧云数据晚到、旧客户端上传、清除后恢复同步等情况下，角色与原有进度符合上述规则。

### 9.1 全线规则

- 第一个地点是真正初见，不能为了“每站重逢”写成“又是你”。
- 玩家是同一个穿越而来的同行者；移除不必要的家世、职业、长期寄居等强制背景。
- 后续开场根据前后场景选择重逢、继续同行或安静照面，不机械重复“又是你”。
- 共同经历只引用确实在更早剧情中发生的内容。分支专属的承诺不能写成所有玩家都说过。
- 固定称呼由场景和相处经历决定，例如“兄台／你／故人／老朋友”，不显示对应等级，不根据外观分配称呼。
- 杜甫可以记得过去，不能知道下一章、未来诗作、自己的结局，也不需要反复讨论玩家为何没有变老。
- 姓名放在 UI 的发言栏与档案；NPC 正文、配音台词、自由对话提示均使用固定称呼。
- 保留诗人核心情绪、历史主线、诗词、知识点与主要分支，改动聚焦角色位置和前后衔接。
- 每站检查“开场、玩家发言、杜甫回应、AI 场景提示、结尾回望”五类位置；已有自然衔接的地方保留，不规定每站硬加四段文字。

## 10. 步骤七：让 AI 记得已发生的共同经历

主要文件：`cloudfunctions/chat/engine.js`、`cloudfunctions/chat/index.js`、`pages/chat/chat.js`。

建议从源稿的结构化配置生成一份前后端可用的杜甫场景／共同经历表，而不是上传整个自由文本档案。每个记忆项包括：稳定 ID、来源地点、简短事实、触发条件及可引用的后续场景。

1. 将 `scenePlayerContext()` 的杜甫分支从“本次临时身份”改为“会在关键人生节点重逢的同一位同行者”。
2. 不再发送或使用 `playerRoleId`、`relationshipStage`、信任分作为杜甫人格条件。
3. AI 不需要知道三张立绘的差异；无需收到自定义姓名，避免模型称呼与固定配音不一致。
4. 共同经历以正式完成的地点为基础。第一版优先记录各分支必经的共同事件，不记录“玩家曾答应某句话”一类未必发生的细节。
5. 若确实引用分支专属选择，必须保存稳定选项 ID 和实际选择证据；目前只有文本或旧迁移状态而无法证明时，使用中性回忆。
6. 服务端从已有用户进度取证并过滤；客户端只提供当前地点、当前 AI 节点和可校验的事件 ID，不把任意客户端“记忆描述”拼入系统提示。
7. 服务端按配置验证当前节点属于当前地点且为 AI 对话节点，并从可信场景配置取提示。杜甫新流程不直接信任客户端自由传入的 `freePrompt`。
8. 可用记忆必须在当前叙事位置之前；同一地点还未出现的诗句和决定也不能提前泄露。需要回溯事件时以节点进度或当前会话完成的稳定事件为依据。
9. 近期对话记录只属于当前地点和本次会话；切地点／进入重温时清空，避免晚年聊天记录带回少年场景。
10. 每次只注入少量与当前场景相关的记忆，例如最多三条短摘要；其余按需选取，不堆满 22 地点全文。
11. 本地通关已完成但云同步未到时，尝试正常同步；仍未确认的个人记忆采用不指名具体事件的故人语气，不阻塞用户对话，也不编造经历。
12. 没有记忆证据时允许自然交谈；不把失败降级成错误职业身份或反复“初次见面”。

示例规则：已正式经历洛阳应举和泰山、正在长安时，可提及那些共同经历；重温泰山时，长安、战乱、成都、湘江的内容即使已经通关也必须排除。

“记得过去”是剧情上下文连续性，不是无限聊天记忆。本轮不新增长期保存用户完整 AI 聊天正文的功能。

完成标准：AI 的称呼、记忆与画面中的玩家角色一致；无法引用未发生事件；三种外观不改变 AI 对玩家的亲疏判断。

## 11. 步骤八：调整配音与素材使用

主要文件：`utils/ttsAudio.js`、`pages/chat/chat.js`、`tools/export-voice-manifest.js`、相关语音清单。

1. 修正地点模式下的音频标识，明确使用 `storyId/locationId/nodeId`；时期模式继续使用原标识，不用时期音频盲目代替同名地点节点。
2. 让清单导出读取当前注册的地点剧本，只导出 NPC 的 `talk` 节点，不把玩家发言当成杜甫配音。
3. 对照步骤六的改稿记录，只重新生成改动过的 NPC 台词；玩家姓名栏和外观变化不需要新增配音版本。
4. 改过台词而音频未更新时，该节点禁用旧音频，继续显示新文字；可通过音频清单记录文本摘要／版本来判断是否匹配。
5. 有条件的回忆对白如果改变 NPC 发声文本，必须匹配对应版本音频；第一版可优先把条件回忆放在旁白或 AI 对话，减少静态配音分叉。
6. 图片仍复用三张现有 PNG，核对透明背景、左右站位、显示尺寸和缓存失效；线上访问失败必须有可用占位。
7. 首次角色说明使用静态文字即可，复用现有穿越视频，不新增每站视频制作任务。

完成标准：文字与实际播放语音一致；缺音频可继续剧情；换名、换形象不导致配音爆炸；地点入口能够正确请求音频。
